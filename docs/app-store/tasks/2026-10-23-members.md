# People on a shared server: B-149 (2026-10-23)

Board row: B-149 in [docs/evidence/backlog.md](../../evidence/backlog.md). Follows B-87 part 2
([2026-10-23-organization-mode.md](2026-10-23-organization-mode.md)): an organization's Access group
could only hold administrators, because every signed-in person was the owner.

## Facts

| Fact | Where |
|---|---|
| Every person Access lets in was the owner at level `admin` | `workers/mcp/keys.ts` (`principalFor`) |
| The web app checked no person beyond Access | `workers/app.ts` (the Access middleware, its old "authorization model note") |
| Mailbox scoping exists for agent keys: routes about one mailbox pass, the feed is narrowed in and out | `workers/mcp/scope.ts` (`scopedApi`, `accountOfPath`, `FEED_ROUTES`) |
| The in-process API calls the API router directly, so a re-dispatched feed read does not meet the app's middleware again | `workers/mcp/handler.ts` (`inProcessApi`, `api.fetch`) |
| A mailbox's own settings (`PUT /api/v1/mailboxes/:id`: forwarding, reply agent, signature) sit under the mailbox's path | `workers/index.ts` |

## Decisions

1. **Access decides who may sign in; a list decides the role.** R2 `config/members.json`, written on the
   etag read like the agent keys. Empty or absent: every person is an administrator, so a one-person
   server changes nothing. Listed: `admin` has every right; `member` reaches its mailboxes; anyone
   else Access lets in gets 403 with a sentence naming who to ask.
2. **A member reaches mail, not the server.** On `/api/*` a route about exactly one of the member's
   mailboxes passes and the feed (`GET /api/inbox`, `/api/accounts`, `/api/inbox/hidden`) is answered
   through `scopedApi` with wording for a person. Refused: every other route, a mailbox's own settings
   and deletion (forwarding alone could send someone else's mail away), an account's disconnect and
   password, `/mcp`, `/agents/*`, the relays, the fabric routes. Pages and assets pass; they hold no data.
3. **Nobody locks the server.** The list always keeps an administrator and never empties (an emptied
   list would make everyone an administrator again); the first change a person makes lists them as an
   administrator. A list that is there but cannot be read lets nobody in (fail closed) and says to
   delete it in R2. A removed person is out within 10 s (the per-isolate cache).
4. **People are changed by a person.** `PUT` and `DELETE /api/members/:email` are in `NOT_TOOLS`, like
   agent keys: who may read whose mail is not an agent's act. `list_members` (admin, read-only) reads it.
5. **The interface follows the role.** `GET /api/me`; a member's inbox loads and shows no categories,
   reply-status setting, Outlook setup, agents' runs, Rules & history, Settings, Add address or Hide;
   Settings shows a page that says it is the administrators'. A server before 0.30.0 has no `/api/me`:
   the app treats the person as the administrator there.
6. **Not in this unit:** a member's own signature and the per-mailbox Spam emptying and discard restore
   (refused with a sentence for now); delegated calls (B-83).
