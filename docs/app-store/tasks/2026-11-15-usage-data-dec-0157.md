# B-285: the Mac app's usage data under the contract's DEC-0157 (UD-1, UD-2)

**Asked:** fabric-agent-contract's announcement `1ca250e1` (2026-11-15): DEC-0157 (CT-216, `main` `8736d21d`) makes
anonymous usage and error data on by default, told once, each product's own switch
(`docs/specification/usage-data.md`, UD-1 to UD-6), and its *Compatibility* names what Fabric Inbox owes. The operator's
decision behind it: 2026-11-04 (on by default, a notice at first start that is not a question, off per product).

## Today (`desktop/analytics.cjs`, `desktop/main.cjs` at `9eda4e6b`)

1. **Sends before the notice.** `start()` sends `app_installed`, `app_started` (and the baseline tier) at launch; the
   notice is shown when a window first comes forward (`askUsageCounts`), so a background start sends first.
2. **Earlier no read at the wrong time.** A shared `analytics: false` is read at every start of an install shown the
   notice whose switch was never set (`state.declined === null && state.disclosedAt`), also after it sent, so another
   app's later off turns it off (review K-7); and never before the first send of a new install.
3. **Unreadable shared file sends anyway.** It runs the baseline tier with no id (B-198).
4. **The notice** says "an id shared by the PassionCode apps" without naming them, nor that the id ties events together,
   that a session id ties a session's, that turning it back on resumes the shared id, or that what was collected since
   start may be sent at once.
5. **README** says the switch turns counts off "for every PassionCode.ai app on the Mac at once" (false since B-200).

## Target

1. **Nothing leaves before the notice (UD-1).** Events are collected from start into the queue (as today, at most 200,
   none older than 23 hours) and nothing is sent until the notice of the current version has been shown. The state keeps
   `noticeVersion`; this change is version 2, so every install, old or new, sees the new notice once. The notice is
   marked shown once it has been open 1.5 s, never waiting on the answer (a notice, not a question); Turn Off pressed
   within that time drops everything before anything leaves, and Turn Off later drops what waits and stops collecting
   (review K-4). A dialog that fails to open marks nothing.
2. **An earlier no (UD-2).** On an install whose own switch the person has not set on (`declined !== false`), each run
   before the first send, or once at this version's first run for an install that already sent (the stand-in run),
   reads the shared file: `analytics: false` there is an earlier no, kept as `declined: true, earlierNo: true`, and what
   was collected is dropped. It is read at each start and again when the notice opens, until the first batch is accepted
   (the first send of this version, which stands in for an install that sent before): only then is `sharedChecked`
   kept and the shared field never read for the switch again (review K-1, K-5). An existing `declined: true` stays an
   own off; nothing invents an `earlierNo` for it (K-7). The person setting the switch on (the menu) ends an earlier
   no without writing the shared file. The menu says why it is off: "Share Usage Details (off: turned off for the
   PassionCode apps on this computer)".
3. **An unreadable shared file holds every send (UD-2).** Any read error other than absence, or content not of the
   shared shape: nothing is sent in that run, the baseline included; the next run reads it again. The app's only
   installation id is the shared one and it never sends without it, so it offers no control there: the menu shows the
   switch on but disabled, with the line "On, but nothing is sent until the shared settings file can be read
   (PassionCode/installation.json)"; Off stays possible there (K-2). The baseline tier without an id (B-198) is retired: there is no case left in which
   it runs.
4. **The notice (UD-1)** says what is collected and why, that the installation id is shared with Fabric, Fabric
   Switchboard, Fabric Dashboards and the PassionCode launcher (as of this version; the maintained list is
   `docs/ANALYTICS.md`, its full address in the notice), that it ties this Mac's events together, and those apps' events, though it names no one; that a
   session id ties one session's events; that the data goes to PassionCode.ai; that what was collected since the app
   started may be sent now; and that Share Usage Details in the menu turns it off for Fabric Inbox only, and turning it
   back on resumes the same shared id.
5. **README** corrected to "for Fabric Inbox only"; `docs/ANALYTICS.md` gains the list of products sharing the id and
   the rules above; AGENTS.md's lifecycle row for usage counts follows.

The agent door to the switch (UD-4, a relayed `change-policy`) is not built: when to build it is the operator's
(DEC-0157 *Compatibility*), and B-236 keeps the row.
